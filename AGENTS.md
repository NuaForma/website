# NuaForma website — Agent Instructions

This repository owns the public static site at https://nuaforma.dev and its downloadable deployment/example kits. Product code, technical module documentation, renderer policy and real runtime qualification belong to [NuaForma/NuaForma](https://github.com/NuaForma/NuaForma). Read adjacent `AGENTS.local.md` if present; it is optional and must remain ignored.

- Preserve existing local, untracked and ignored files. Never copy secrets, private documents/fonts, caches or operator extensions into this public repository.
- Follow the product's [stable-component and upgrade-debt policy](https://github.com/NuaForma/NuaForma/blob/develop/ARCHITECTURE.md#stable-components-and-upgrade-debt): prefer current suitable stable tooling/components with exact reviewed pins and real checks; retain older versions only for evidenced compatibility or reproduced problems with explicit tracked reassessment/removal conditions. Do not introduce avoidable workarounds, silent exceptions or weakened gates. Runtime/profile snapshots still come only from an actually reviewed immutable product release, never an independent "latest" substitution.
- Use `develop` for routine work and feature PRs. `main` is the deployed website. Promote prepared site changes through a checked PR once the advertised product artifacts are actually public. Main-only emergency corrections must be brought back to develop through a PR.
- Always sign commits and use Conventional Commits. Normal work uses PRs and the required `Website checks` check. The maintainer explicitly permits exceptional small, signed direct pushes to main by repository administrators. This is not blanket authorization to bypass review; never bypass signatures, force-push protection or branch-deletion protection. A failed check must prevent Pages deployment even after an emergency push.
- Git/deployment/settings actions still require user authorization for the task. Repository ownership is not authorization. Do not publish product binaries or create product tags from here.
- Before a PR, assess documentation and Playground impact, update relevant material and explain when no update is needed. Retain development-only warnings and production/Playground separation.
- Preserve existing public URL paths. Keep published downloads aligned with actual released library/image versions and native architectures; do not advertise unreleased capabilities. No hosted generation or live demo runs on this site.
- Preserve reviewed container isolation settings, limits, mounts, notices and exact pinned image digests. `reference/runtime` contains immutable-release profile inputs with a checksum manifest; update them only from an explicitly reviewed product release, never to make a test pass. They are not independently maintained security policy.
- Prefer bounded static QA: `python3 tools/site/check_site.py`, `python3 tools/site/check_reference.py`, `python3 -m unittest discover -s tools/site -p 'test_*.py'`, `node --check site/app.js` and `node --test tools/site/test_tabs.cjs`. Check all four Compose kits and their AppArmor overrides. Repackage changed sources and verify every ZIP member against its source.
- Do not author/regenerate Word examples or run requests merely to migrate/format the site. When document content actually changes, use the documented authoring and product qualification procedures and report structural versus visual evidence honestly. Optional document-authoring tools are not production dependencies.
- Keep the established branding, light/dark themes, accessible independent tab groups and relative static links. Keep the technical documentation in the product repository instead of duplicating it.
- Only main may deploy through the protected `github-pages` environment, after successful site checks. Verify the live HTTPS page and matching download checksums before reporting a release/site handoff complete. Do not change the custom domain, DNS or HTTPS settings without explicit task authority.

See [ARCHITECTURE.md](ARCHITECTURE.md), [README.md](README.md) and [CONTRIBUTING.md](CONTRIBUTING.md). Historical product commits are retained unchanged as ancestry to preserve existing history and signatures; their old product instructions do not govern this repository's current website-only tree.
