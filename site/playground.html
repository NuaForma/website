01 · GET STARTED

From download
to first document.

Use the development Playground image. The production image contains the API without the Playground interface.

1. Choose your machine

Download and extract the AMD64 kit for Intel/AMD, or ARM64 for Apple Silicon and other ARM64 systems. Create the custom-fonts and extensions folders beside its Compose file.

Playground AMD64 kit ↓Playground ARM64 kit ↓

2. Start the Playground

Run from the extracted folder:

docker compose up -d

Open http://localhost:8080/playground/ in your browser. Choose either the production or Playground kit for port 8080.

3. Add a template and data

Choose DOCX or PDF output, upload your Word template and enter its JSON data. Inspect the available providers and options. Start with the synthetic example kit if you do not yet have a template.

4. Generate and download

Generate the document, then download the result. Export the JSON request and curl instructions to repeat it from your application or terminal. The template and resource files remain separate uploads.

02 · TRY AN EXAMPLE

Small changes.
Visible results.

Type these markers as ordinary text in Word. Paste the data into the Playground, generate, then change one value and try again.

A field

Dear {customer.name},

With the data below, the name becomes Ada Lovelace.

A condition

{#if approved}Approved{#else}Draft{/if}

Change approved from true to false to switch the text.

A formatted date

{issuedOn | date("dd-MM-yyyy")}

The date becomes 28-10-2026. See the date and time reference for other patterns.

Data for all three

Playground data
{
  "customer": {"name": "Ada Lovelace"},
  "approved": true,
  "issuedOn": "2026-10-28"
}

Want a fuller test? The seven downloadable scenarios include nested conditions and loops, null values, watermarks, Word output and images. The template guide explains the supported syntax and Word structure rules.

03 · CHOOSE FONTS

Use the fonts
your template needs.

Inspect what is available

The provider explorer and font controls list the available families and faces. Bundled fonts need no upload. Mounted fonts can be selected through their resource IDs.

Supply a missing face

Upload a standalone TTF or OTF face and enter its actual family, style and resource ID. The Playground adds the font declaration and binary resource together. Font selection supplies a font; it does not rename or replace the font used in Word.

PDF output embeds the used faces and checks technical embedding permissions. Names alone do not guarantee glyph coverage. See fonts and operations for deployment guidance.

04 · FIND AN ERROR

See where
the parser stopped.

In 0.4.0-alpha.4, inspect the source location, download a marked DOCX or diagnostic PDF, or preview malformed fragments with the first actual parser error marked precisely. Normal generation remains strict. Marked diagnostic PDFs remain available from 0.3.0-alpha.4.

One reliable error at a time. Generation remains unsuccessful. The diagnostic PDF is a literal copy of your template with the first locatable error marked; template instructions are not filled with your data. Correct the original Word file, generate again and inspect the next error if there is one.

1. Generate the failing template

For a deliberate test, remove the closing brace from a field such as {customer.name}. The error response shows the reason, parser excerpt, request ID and available Word location.

2. Download the diagnosis

Choose Download diagnostic PDF. The Playground uses the original failed upload. A red ERROR 1 marks the source fragment, and an extra page explains what the parser read.

When PDF creation fails

Choose Download marked DOCX. It marks the first located paragraph with [ERROR 1] and appends the concrete reason and source coordinates. This inspection copy does not require native PDF layout, fonts or PDF validation. Unsafe packages or serialization errors can still prevent inspection.

Inspect malformed fragments

Preview with error markers (DOCX) keeps malformed text literal and marks only the first actual parser failure with [ERROR 1] at its source position, with a reason, part, paragraph and bounded excerpt in the appended report. Other malformed fragments remain literal; independently valid fragments are evaluated. Structural if/each regions remain literal with [LITERAL BLOCK]; no branch is guessed. Ordinary generation remains strict. This is a diagnostic copy, not a completed document.

Source details identify the logical DOCX part, paragraph, XML path and a bounded, secret-aware excerpt when available. XML coordinates are not Word page numbers; missing locations are not invented. Development responses and GENERATION_REJECTED logs expose these details and the concrete rejected package-part name when it can safely be shown. Use the request ID to find the matching event. Production omits excerpts and has no inspection routes. Downloads contain private document/data content: protect them and your development instance. See the complete diagnostic guide ↗.

Passive Word bookmarks, spelling/grammar markers and cached page hints do not interrupt visible template expressions in 0.4.0-alpha.4, including cached hints within mixed runs. Actual tabs, manual breaks, fields, hidden text and paragraph/container boundaries still separate fragments. Correct the first marked error in the original document and generate again.

The Playground uses the NuaForma favicon. Passive Word metadata and qualified compatibility settings are supported in 0.4.0-alpha.4. Supply the licensed font faces actually required by the supported visible content and paragraph marks: missing required faces fail explicitly instead of being substituted. Formatting-only empty runs no longer require unused fonts. See the font and deployment instructions.

05 · CLEAN A TEMPLATE

Keep a copy.
Review what changed.

Available in 0.4.0-alpha.4, the development Playground can remove unsupported DOCX parts, objects and formatting from a separate template copy. You decide whether the result is acceptable in Word.

1. Download a clean copy

Select your DOCX, open Clean a template for native PDF below the file selector, and choose Clean template and download report. Only the template is sent; JSON data and uploaded fonts/resources are not used. Your original file is unchanged.

2. Inspect the ZIP

cleaned-template.docx contains the copied template. Remaining variables, pipes, if/each blocks and even malformed markers stay literal. Unsupported containing objects can be removed with their text. cleanup-report.txt lists every removal or restoration, its package part, available XML location and reason.

3. Review or report

Open the copied DOCX in Word and read the report before replacing the original. Unsupported visible content or styling may be lost, and required supported defaults may be restored. The report can help explain missing functionality in an issue; review identifying names/locations before sharing it. Include the NuaForma version and a small, non-confidential example where possible.

Version 0.4.0-alpha.4 retains qualified signed/hanging indents, paragraph-mark metrics and measured header/footer bands, including supported EMF logos and footnotes. Unsupported image constructs can still be removed; inspect the report and copied document. Technical checks establish native source-profile support; you alone accept the contents and appearance. Required fonts and normal template syntax/data checks still apply when generating PDF. Unsafe or unresolved packages, cancellation and exceeded limits do not produce a cleaned template. This tool is absent in production; ordinary generation remains strict. See the complete cleanup guide ↗.
